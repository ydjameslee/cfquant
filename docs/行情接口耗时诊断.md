# 行情接口耗时诊断

网页「接口 → 行情数据」会在结果上方显示分阶段耗时。以下三个接口的成功响应在 `data.timing` 返回明细，路由执行失败时在顶层 `timing` 返回已取得的明细：

- `POST /api/data/full-tick`
- `POST /api/data/market`
- `POST /api/data/market-ex`

需要更新并重新加载 Web 服务和对应的 QMT 桥接脚本。极致模式的策略内嵌桥接代码，需要重新部署并启动新版策略；仅刷新网页不能更新 QMT 内正在运行的代码。通用、高级和极致模式使用相同的计时口径。

| 字段 | 计时范围 |
| --- | --- |
| `request_id` | 最后一次 RPC 的请求 ID，可对应 QMT 日志 |
| `qmt.available` | 是否收到了 QMT 侧的计时明细 |
| `qmt.queue_ms` | QMT 桥接解析请求后，到开始执行行情动作的等待时间；包含普通通道的队列与派发等待 |
| `qmt.native_ms` | 调用 QMT 原生取数函数的累计时间，包含函数内部的等待；无法继续区分其内部网络、磁盘或计算 |
| `qmt.native_calls` | 各次原生调用的方法名、耗时和是否成功，可识别先调用旧接口、再调用扩展接口的情况 |
| `qmt.convert_ms` | cfquant 将扩展行情结果转换为旧行情接口形状的时间 |
| `qmt.execute_ms` | QMT 桥接执行行情动作的总时间，已包含 `native_ms` 和 `convert_ms`；不含排队与结果编码 |
| `qmt.encode_ms` | QMT 侧将结果对象编码为协议数据结构的时间，例如 DataFrame 转行列列表；不含最终 JSON 文本序列化和发送 |
| `qmt.fallback_used` | 旧行情接口缺失或返回不可用结果，是否回退到扩展接口 |
| `rpc.wait_ms` | Web 内的 RPC 客户端从连接/发送开始，到取得响应的时间；含锁等待、通道往返、QMT 排队和处理、接收端 JSON 解析，不能当作纯传输耗时 |
| `rpc.decode_ms` | RPC 客户端把协议结果还原成 Python 对象（如 DataFrame）的时间 |
| `rpc.total_ms` | 单次 RPC 总时间，包含上述等待和解码 |
| `web.route_ms` | Web 选择账号、路由、执行 RPC 和必要重试的总时间 |
| `web.result_convert_ms` | Web 将返回结果转换为可输出 JSON 的 Python 数据结构的时间，包含 DataFrame 转字典；不含最终 JSON 文本序列化和 HTTP 发送 |
| `attempts` | 本次请求内每次实际 RPC 尝试的路由、请求 ID 和计时；顶部 `qmt`、`rpc` 对应最后一次尝试 |

所有时长单位均为毫秒，使用各进程的单调时钟测量，不依赖 Web 和 QMT 的系统时间同步。各阶段存在包含关系，不能全部相加。网页另外显示页面往返时间，包含服务端最终序列化、HTTP 往返和浏览器接收解析。

`full-tick` 和 `market-ex` 无需旧接口格式转换，`convert_ms` 通常为 0；这表示该步骤没有执行，不代表原生取数没有成本。QMT 内部的数据类型转换属于原生函数耗时，无法由桥接层单独测量。

如果超时前没有收到 QMT 回包，`qmt.available` 为 `false`，`reason` 为 `no_response`，不会虚构原生执行或转换用时。新版 Web 连接旧桥接脚本仍能正常取数，但会提示「桥接脚本未提供」计时（`bridge_timing_unavailable`）。使用本地数据源时标记 `local_data_source`。

启用桥接日志后，每次行情动作执行结束会记录 `market_timing action=... id=... queue_ms=... native_ms=... convert_ms=... execute_ms=...`。请求超时后若 QMT 后来完成，可用返回的请求 ID 查找这条日志；仍在阻塞或未执行完的调用尚无完成耗时。

定位时先看 `queue_ms` 是否高，再看 `native_calls`。若原生取数很快，而 `convert_ms`、`encode_ms`、`decode_ms` 或 Web 转换时间高，应检查结果规模和数据形状。即使 RPC 总等待很高，也不能据此直接断定是管道带宽瓶颈。
