# 低延迟链路升级（2026-10-17）

这次改造覆盖 Web 路由、极致模式发送、PipeHub、网页推送、缓存与 QMT 调度。极致模式仍在 QMT 定时器/回调线程执行 QMT API；后台发送线程只接收已编码的不可变字符串，不持有待处理的原生行情对象。

## 六个方向

1. **Web 路由并发**：独立客户端可以并行等待 RPC。相同客户端的请求保持到达顺序，指向同一账号与账号类型的交易请求也保持到达顺序。队列满时明确返回错误。只读请求在排队期间耗尽超时预算，会在派发前失败；不会用这一机制取消下单或撤单。
2. **独立发送队列**：QMT Pipe 客户端、Hub 的每个接收连接、每个 WebSocket 使用独立 FIFO 写线程。慢连接不再占用其他连接的写线程。队列满、写失败或 Pipe 发送超时时断开对应连接；已接受但尚未写出的包随连接终止，不转投新连接、不静默覆盖旧行情、不自动重放订单。
3. **减少重复转换与编码**：`ok()` 已经转成网页 JSON 的结果不会在 HTTP 输出时再次递归转换；带纯 JSON 标记的全推也跳过重复递归遍历，后续添加了特殊对象时仍使用兼容转换。WebSocket 同一批广播只转换、编码、组帧一次，各连接共享不可变字节。原有 xtquant 类型还原及网页字段结构保持兼容。
4. **缩短 Hub 转发路径**：新版 QMT 在外层信封标记事件路由，Hub 按目标频道转发完整内部字符串，不再解析整批行情；旧信封仍走兼容路径。状态文件写入移到后台并合并，使用临时文件原子替换。默认关闭逐请求成功日志，保留连接和异常日志。
5. **控制长期内存积压**：网页普通行情历史仍保留原有最多 1,000 批数据，内部延迟诊断保留最近 2 批。按编码后字节数控制内存，旧批次写入外部 Python 的临时文件，查询时还原。SDK 用户回调仍串行执行，积压超过内存预算时保存原始消息到临时文件，顺序读取，不丢弃交易回报或中间行情批次。消费、取消订阅、关闭时回收相应数据与临时文件。
6. **QMT 公平调度与查询复用**：每轮请求泵默认预算 5 ms，检查点在请求之间，不中断正在执行的 QMT API。已有同参数账户查询合并机制现在复用一次结果编码。过期且尚未开始的只读查询不再调用 QMT；同组其他未过期等待者仍可正常取数。三份独立极致脚本与公共实现同步。

绑定界面的默认定时器间隔仍为 **1 ms**。每轮 5 ms 处理预算与定时器间隔含义不同：前者限制连续处理积压请求的时间，后者是调度请求间隔。一次原生调用或编码如果超过 5 ms，会完成后再让出执行机会。两者都不构成实际延迟上限。

## 故障与兼容边界

- 同步下单仍等待原有订单确认条件，异步下单仍按原有序号及回调返回。后台入队成功不代表订单成功。
- Web 的连接恢复自动重试限定为同步只读查询。下单、撤单、订阅、下载以及异步查询不会因断线而自动重放；交易结果不明确时应查询委托并核对回调。
- 新增发送缓冲上限包括正在发送的包。Pipe 按 Python 字符串占用估算，WebSocket 按帧字节计数，不是整个进程 RSS 的硬上限；编码临时对象与正在执行的用户回调另占内存。
- SDK 容许单批大行情驻留内存，避免正常全推每批都写磁盘；只有形成积压才启用临时存储。因此内存预算不是单条消息大小限制。
- 临时文件位于外部 Python 的系统临时目录，不在 QMT 内写磁盘。它们不是断电恢复日志。SDK 回调积压持续增长时可能耗尽磁盘；保存失败会明确断开连接并唤醒等待的 RPC。网页历史保存失败会在状态中报告 `history_error`，历史查询返回错误，实时广播继续；重新订阅清理历史后可以恢复。
- Web 历史文件按原有批次数量保留和回收，而非无限归档。压缩死区会带来外部 Python 的磁盘开销。SDK 用户回调本身很慢时，搬动队列不能消除其处理时间。
- 新版 QMT 信封对旧 Hub 仍可按原有协议处理；完整收益需要同步更新 Hub、Web、SDK 和 QMT 脚本。线程之间仍可能竞争 GIL；本次没有宣称移除了所有序列化开销。

## 配置

以下为进程环境变量，修改后重启对应进程。QMT 继承的环境需在 QMT 启动前设置；绑定界面原有的定时器与日志开关继续生效。

| 配置 | 默认值 | 作用范围 |
| --- | --- | --- |
| `CFQUANT_WEB_ROUTE_WORKERS` | 8 | Web 独立请求工作线程数 |
| `CFQUANT_WEB_ROUTE_MAX_PENDING` | 1024 | Web 等待派发的请求数上限，不含执行中请求 |
| `CFQUANT_PIPE_SEND_MAX_BYTES` | 134217728 | QMT Pipe / Hub 每连接发送缓冲估算上限 |
| `CFQUANT_PIPE_SEND_TIMEOUT` | 15 秒 | QMT Pipe / Hub 最旧发送包等待与发送累计时限；0 关闭时限，不关闭容量限制 |
| `CFQUANT_WS_SEND_MAX_BYTES` | 134217728 | WebSocket 每连接发送缓冲上限 |
| `CFQUANT_PIPE_STATUS_INTERVAL` | 0.25 秒 | Hub 状态写盘合并间隔，最小 0.05 秒 |
| `CFQUANT_PIPE_HUB_VERBOSE_RPC` | 0 | 设为 1 恢复每次 RPC 成功日志 |
| `CFQUANT_WEB_QUOTE_HISTORY_BYTES` | 67108864 | 每个 Web 行情历史存储的内存预算，按编码后字节计 |
| `CFQUANT_CALLBACK_MEMORY_BYTES` | 67108864 | 每个 SDK 回调队列的估算内存预算 |
| `CFQUANT_CTYPE_NORMAL_PUMP_MAX_MS` | 5 | Pipe / 极致入口普通请求泵每轮预算，0 保留不按时间限额的行为 |
| `CFQUANT_CTYPE_TRADE_PUMP_MAX_MS` | 5 | Pipe / 极致入口交易请求泵每轮预算 |

发送队列另有每连接 1,024 帧上限，不会无限堆积。SDK 回调队列保留所有已接收事件，超过内存预算使用磁盘；无法在有限资源下承诺无限期保留无限积压。

## 定位延迟

- 网页行情接口：`QMT 结果编码` 现在覆盖对象转换、JSON 规范化和 JSON 编码，`其中 JSON 编码` 是其子项。统计口径扩大，升级前后应结合端到端耗时比较。RPC 返回 `json_decode_ms`，它已经包含在 RPC 等待中；结果类型还原 `decode_ms` 另计。HTTP `Server-Timing: web_json;dur=...` 单独报告 Web 最终 JSON 编码，并显示在接口调试页面。
- `cfquant.status`：查看 `send_queue`、`request_queue_size`、`expired_readonly_requests`、`pump_max_ms`。
- Hub 状态文件：`send_queues` 提供缓冲字节、发送中状态、最旧包年龄、最近排队时间和写入时间。状态文件是事件触发的后台快照，需结合其更新时间阅读；不是每次查询都实时生成。
- `GET /api/lttx`：`request_queue` 提供 Web 排队信息；`callback_queues` 提供 Web 内部 SDK 的回调积压、临时文件字节和最近用户回调耗时。
- `GET /api/quotes/status` 与 `GET /api/diagnostics/quotes/status`：查看 `history` 和 `history_error`。
- 用户 SDK 底层 RPC 客户端的 `callback_status()` 提供同样的回调队列指标。`oldest_age_ms` 持续增长通常说明消费速度低于到达速度，单纯缩小 QMT 定时器不能解决。

## 本地验证与部署

专项回归使用假 QMT、内存连接与隔离配置，覆盖 FIFO、慢连接隔离、过载断线、断线后不重放、读请求过期、合并查询错误广播、订阅首包和取消、回调临时文件、退出清理及数据类型。独立脚本保持 GBK / CRLF 和 Python 3.6 语法，并检查生成器幂等性与 QMT 无文件 I/O。

可复现基准：

```powershell
python tools/benchmark_latency_pipeline.py --count 26475 --repeat 3
```

本机 Python 3.12.4，26,475 只模拟标的、7,810,145 字节 HTTP JSON，三次中位数：

| 独立处理阶段 | 改造前 | 改造后 |
| --- | ---: | ---: |
| `ok()` 之后的 HTTP 转换与编码 | 503.339 ms | 149.238 ms |
| 同一批行情向三个网页客户端准备广播 | 1,622.556 ms | 149.349 ms |
| 六个合并查询等待者的回包编码 | 7,232.048 ms | 1,203.764 ms |

同批行情在 Hub 的一次内部 JSON 解析约 171.934 ms，新信封转发路径省去此步骤。基准校验前后数据一致。各行是独立场景，不能相加，也不是实际下单、交易时段全推或网络端到端时延。

使用时需更新外部 cfquant SDK、Web 与 PipeHub，然后在绑定界面重新部署极致策略并重启策略。独立 SH / SZ 入口都需更新。确认新状态中的 `pump_max_ms=5` 与 `send_queue`，再在交易时段对比相同标的、相同参数的 P50/P95、全推内部延迟与队列最旧包年龄。单次本地基准不能替代长期行情压力复测。
